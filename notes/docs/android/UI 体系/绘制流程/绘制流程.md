>  一共分为三个绘制流程：measure / layout / draw

## 驱动流程

三个阶段的调度者是 **`ViewRootImpl.performTraversals()`**，它由 `Choreographer` 在 VSYNC 信号到来时回调（`CALLBACK_TRAVERSAL`）：

```
scheduleTraversals()          // requestLayout / invalidate 最终都会走到这里
   └─ Choreographer.postCallback(TRAVERSAL, mTraversalRunnable)
        └─ doTraversal() → performTraversals()
             ├─ performMeasure(childWidthMeasureSpec, childHeightMeasureSpec)
             ├─ performLayout(lp, mWidth, mHeight)
             ├─ performDraw()
             └─ 之后再执行 Handler 里的 Runnable / 通知 GlobalLayoutListener
```

`performTraversals()` 是"一切都在这里发生"的超级方法：计算窗口尺寸、`relayoutWindow()`（向 WMS 申请 Surface）、处理 `requestLayout` 的 RunQueue（子线程调 `requestLayout` 时会入队到这里执行），然后依次测量、布局、绘制。

三个阶段的共同特征：**都是自上而下的递归，都由父容器主导，子 View 只能"被测量、被摆放"**。父容器在 `onMeasure/onLayout/dispatchDraw` 里遍历子 View 调用对应的 `measure/layout/draw`，形成深度优先的递归。

## 1. Measure（测量）

### 入口与契约

```java
public final void measure(int widthMeasureSpec, int heightMeasureSpec)  // final，不可重写
protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec)   // 重写点
protected final void setMeasuredDimension(int w, int h)                 // 必须调用
```

`measure()` 是 `final` 的：它负责**缓存判断 + 状态维护**，把真正的"算多大"交给 `onMeasure()`。这是模板方法模式的标准用法。

### MeasureSpec：父对子的"期望 + 约束"

一个 32 位 int 打包两部分（`MODE_SHIFT = 30`）：

```
高 2 位 = mode，低 30 位 = size
EXACTLY     : 父已定死，子的 size 就是最终值（match_parent / 固定 dp）
AT_MOST     : 子上限是 size，可以更小（wrap_content）
UNSPECIFIED : 随便你多大（ScrollView 里的子 View、ListView 的 item）
```

View 的最终尺寸由 `resolveSizeAndState()` / `getDefaultSize()` 决定，`getDefaultSize` 的逻辑很关键：

```java
public static int getDefaultSize(int size, int measureSpec) {
    switch (MeasureSpec.getMode(measureSpec)) {
        case MeasureSpec.AT_MOST:
        case MeasureSpec.EXACTLY:
            return specSize;          // 直接取 specSize
        case MeasureSpec.UNSPECIFIED:
            return size;              // 用默认尺寸
    }
}
```

所以**自定义 View 必须自己处理 `AT_MOST`**，否则 `wrap_content` 会退化成 `match_parent`

### 父容器如何生成子 Spec：getChildMeasureSpec

`ViewGroup.getChildMeasureSpec(parentSpec, padding + margins, childDimension)` 是一个二维查表：

| 子的 LayoutParams \ 父 mode | EXACTLY | AT_MOST | UNSPECIFIED |
|---|---|---|---|
| 固定值（如 `100dp`） | EXACTLY 100dp | EXACTLY 100dp | EXACTLY 100dp |
| `match_parent` | EXACTLY parentSize | AT_MOST parentSize | UNSPECIFIED（新版给 0，老版给 parentSize） |
| `wrap_content` | AT_MOST parentSize | AT_MOST parentSize | UNSPECIFIED 0 |

要点：
- 父传入的 `size` 要**先减去 padding 和 margin**，这是子可用空间的真实值；
- `AT_MOST` 对 `match_parent` 和 `wrap_content` 看起来"一样"，但子 View 的行为不同（一般 ViewGroup 会对 `match_parent` 直接给满，对 `wrap_content` 取内容尺寸）；
- `UNSPECIFIED` 是"无限"信号，会出现兼容分支（`sUseZeroUnspecifiedMeasureSpec`，按 targetSdk 区分）。

典型容器实现：
- `FrameLayout`：遍历子，`measureChildWithMargins()`，再取 `max(childMeasured + margin)` 并 `resolveSizeAndState`；
- `LinearLayout`：**有 weight 时会测量两遍**——第一遍按 `UNSPECIFIED`/剩余空间量，算出剩余空间后按权重分配，再对 weight 子 View 用 `EXACTLY` 第二次 `measure()`；
- `RelativeLayout`：因为依赖关系，常常需要两遍（水平/垂直各一遍）；
- `ScrollView`：对子 View 传 `UNSPECIFIED`，让子"想多高就多高"；
- `RecyclerView`：测量由 `LayoutManager` 接管。

### measure 的缓存与失效：私有标志位

`View.measure()` 内部靠几个 `mPrivateFlags` 决定是否跳过重测：

| Flag | 含义 |
|---|---|
| `PFLAG_FORCE_LAYOUT` | 强制重新测量（`requestLayout()` 设置） |
| `PFLAG_LAYOUT_REQUIRED` | 布局阶段需要重新摆放 |
| `PFLAG_MEASURED_DIMENSION_SET` | `setMeasuredDimension` 已被调用（**没调用会抛异常/被警告**） |

跳过逻辑大致是：如果 `(mPrivateFlags & PFLAG_FORCE_LAYOUT) != PFLAG_FORCE_LAYOUT` 且 spec 与上次相同（`mMeasureCache` 命中），就直接 `return`。所以 **spec 相同且没有 requestLayout 时，measure 会被跳过**。

### requestLayout 的传播

```java
public void requestLayout() {
    if (mMeasureCache != null) mMeasureCache.clear();
    mPrivateFlags |= PFLAG_FORCE_LAYOUT;
    mPrivateFlags |= PFLAG_LAYOUT_REQUIRED;
    if (mParent != null && !mParent.isLayoutRequested()) {
        mParent.requestLayout();   // 逐级上抛，直到 ViewRootImpl
    }
}
```

`ViewRootImpl.requestLayout()` → `scheduleTraversals()`。所以子 View 调 `requestLayout` 会让**整条祖先链**重新 measure/layout（容易造成性能问题，也是"嵌套里 requestLayout 引发全树重测"的根因）。

> 在 `onMeasure` 里调 `requestLayout()` 会导致无限循环；正确做法是改完参数后用 `post { requestLayout() }` 或直接 `invalidate()`。

> invalidate 与 requestLayout 的区别: [[invalidate#与 `requestLayout()` 的区别| here]]

## 2. Layout（布局）

### 入口与契约

```java
public void layout(int l, int t, int r, int b)      // 可重写，但一般不改
protected void onLayout(boolean changed, int l, int t, int r, int b)  // ViewGroup 抽象方法
```

`layout()` 做的事：
1. `setFrame(l, t, r, b)`：写入 `mLeft/mTop/mRight/mBottom`，如果尺寸变了返回 `true`；
2. 尺寸变化时回调 `onSizeChanged(w, h, oldw, oldh)`；
3. 若 `changed` 或 `PFLAG_LAYOUT_REQUIRED`，调用 `onLayout(...)`；
4. 处理 RTL（`resolveRtlPropertiesIfNeeded()`）；
5. 若发生改变，触发自身的 `invalidate()`。

### onLayout：父决定子的位置

`ViewGroup.onLayout()` 是**抽象方法**，每个容器必须实现。典型写法：

```java
@Override
protected void onLayout(boolean changed, int l, int t, int r, int b) {
    int childTop = getPaddingTop();
    for (int i = 0; i < getChildCount(); i++) {
        View child = getChildAt(i);
        if (child.getVisibility() == GONE) continue;
        int w = child.getMeasuredWidth();
        int h = child.getMeasuredHeight();
        child.layout(getPaddingLeft(), childTop, getPaddingLeft() + w, childTop + h);
        childTop += h;
    }
}
```

关键点：
- **`layout()` 必须用 `getMeasuredWidth/Height` 作为尺寸**，位置可以由父任意给（可以重叠、可以超出父边界）；
- `GONE` 的子 View 既不 measure 也不 layout（`VISIBLE`/`INVISIBLE` 都参与 measure，INVISIBLE 只是不绘制）；
- 子 View 在 `onLayout` 里再次调 `layout()` 是允许的，但也可能被父覆盖；
- 布局阶段**不产生绘制指令**，只是确定几何位置。

### 几个易混点

| 方法 | 时机 | 说明 |
|---|---|---|
| `getMeasuredWidth()` | measure 之后 | 测量得到的"想多大" |
| `getWidth()` | layout 之后 | `mRight - mLeft`，"实际多大" |
| `onSizeChanged()` | layout 中尺寸变化时 | 初始化尺寸相关资源的正确位置 |
| `isLayoutRequested()` | — | 是否被标记需要重新布局 |
| `ViewTreeObserver.OnGlobalLayoutListener` | layout 完成后 | 拿到最终尺寸的安全时机 |

在 `onCreate()` 里 `getWidth()` 一定为 0——因为还没经历 measure/layout。正确做法：`view.post{}`、`doOnPreDraw`、或 `OnGlobalLayoutListener`。

## 3. Draw（绘制）

### View.draw() 的六步

```java
public void draw(Canvas canvas) {
    // 1. 绘制背景
    drawBackground(canvas);
    // 2. (旧版本) 保存 layer，为渐隐边缘做准备
    // 3. 绘制自身内容
    onDraw(canvas);
    // 4. 绘制子 View
    dispatchDraw(canvas);
    // 5. (旧版本) 绘制渐隐边缘并恢复 layer
    // 6. 绘制装饰（滚动条、前景）
    onDrawForeground(canvas);
    // 7. (API 26+) 默认焦点高亮
}
```

对应关系：
- `onDraw()` —— **View 自己画自己**（自定义 View 的主要重写点）；
- `dispatchDraw()` —— **ViewGroup 遍历子 View 调用 `drawChild()`**（`View` 里是空实现，`ViewGroup` 重写）；
- `onDrawForeground()` —— scrollbar、`android:foreground`、`onDrawForeground` 的绘制。

顺序决定了层级：**背景最底，内容是中层，子 View 在中上层，装饰在最上**。所以子 View 永远盖在父 View 的内容之上。

`dispatchDraw` 里子 View 的绘制顺序：
- 默认按添加顺序（后添加的盖在上面）；
- API 21+ 支持 **Z 轴排序**（`elevation`/`translationZ`），`ViewGroup` 会构建有序子列表，可重写 `getChildDrawingOrder()` 自定义；
- 带 `Matrix` 变换/动画的子 View（`rotation`、`scaleX`、`translationX`）在 `drawChild` 前通过 canvas 变换应用，**这些属性动画不会触发 measure/layout**——这正是做动画性能优化的核心：用 `translationX` 而不是 `left/right`（后者每次都要 requestLayout）。

### [[invalidate]] 与 requestLayout 的区别

| | invalidate() | requestLayout() |
|---|---|---|
| 触发阶段 | 只 draw | measure → layout（→ draw） |
| 标志位 | `PFLAG_DIRTY` / `PFLAG_INVALIDATED` | `PFLAG_FORCE_LAYOUT` / `PFLAG_LAYOUT_REQUIRED` |
| 传播 | 上抛到 ViewRootImpl 标记 dirty，限定脏区域 | 上抛到 ViewRootImpl，scheduleTraversals |
| 场景 | 颜色、文字变化 | 尺寸、位置、padding/margin 变化 |

注意：`performTraversals()` 末尾**总会执行 `performDraw()`**，所以 `requestLayout` 之后通常也会伴随一次绘制。

### [[硬件加速]]下 draw 的真实含义

从 API 21（Android 5.0）开始默认硬件加速，这彻底改变了 draw 的语义：

```
performDraw()
 ├─ 软件绘制：drawSoftware() → Surface.lockCanvas() → 直接往 Bitmap 上画
 └─ 硬件加速：ThreadedRenderer.draw()
       └─ updateRootDisplayList()：遍历 View 树
            └─ View.updateDisplayListIfDirty() → 把 onDraw/dispatchDraw 的 Canvas 
               操作"录制"成 DisplayList（RenderNode 树）
       └─ RenderThread.syncAndDrawFrame()：在渲染线程真正提交给 GPU
```

要点：
- UI 线程里的 `Canvas` 实际是 `RecordingCanvas`，**onDraw 里的绘制调用只是录制，不是立即执行**；
- 每个 View 对应一个 `RenderNode`，持有自己的 DisplayList；`invalidate()` 时如果只是属性变化（如 `setAlpha`），可以直接更新 RenderNode 而不重新录制；
- **UI 线程负责 measure/layout/录制，RenderThread 负责上传 GPU**，这就是为什么主线程卡顿时滑动会掉帧但不至于完全冻结（渲染线程仍在出帧）；
- `canvas.drawXxx` 的层级由 `saveLayer` 决定离屏渲染，滥用会显著变慢（`onDraw` 里避免创建对象、避免 `saveLayer`）。

## 4. 三个阶段的对比总结

| | Measure | Layout | Draw |
|---|---|---|---|
| 目的 | 决定"我要多大" | 决定"我摆在哪" | 决定"我长什么样" |
| 入口 | `measure()` (final) | `layout()` | `draw()` |
| 重写点 | `onMeasure()` | `onLayout()`（ViewGroup 抽象） | `onDraw()` / `dispatchDraw()` |
| 父容器的角色 | 生成子 MeasureSpec | 调用子 `layout(l,t,r,b)` | 调用子 `draw()` |
| 递归方向 | 自上而下（自下而上回传尺寸） | 自上而下 | 自上而下 |
| 缓存/跳过依据 | `PFLAG_FORCE_LAYOUT` + MeasureCache + spec | `PFLAG_LAYOUT_REQUIRED` | DisplayList / RenderNode |
| 触发方式 | `requestLayout()` | `requestLayout()` | `invalidate()` |
| 读取结果 | `getMeasuredWidth/Height()` | `getWidth/Height()` | — |

> **`requestLayout()` 从当前 View 沿父链上抛到 `ViewRootImpl`，在下一个 VSYNC 由 `performTraversals()` 依次执行 measure（父生成 Spec、子算尺寸、回传）、layout（父读子的 measured 尺寸并摆放）、draw（父先画背景/内容，再递归画子，最后画装饰）；硬件加速下 draw 被拆成"UI 线程录制 DisplayList + RenderThread 提交 GPU"两个阶段。**

## 5. 需要注意的点

1. **`wrap_content` 失效**：自定义 View 未处理 `AT_MOST`，直接用 `specSize`。用 `resolveSize()` 修正。
2. **`onCreate` 里拿不到宽高**：用 `view.post{}` 或 `OnGlobalLayoutListener` / `OnPreDrawListener`。
3. **measure 多次**：嵌套 weight 的 `LinearLayout`、`RelativeLayout` 的双遍测量；用 `ConstraintLayout` 打平层级，或减少无谓的 `requestLayout`。
4. **`onDraw` 里 new 对象 / 做耗时计算**：会拖慢录制帧率；预计算到成员变量。
5. **`requestLayout` 写进 `onMeasure`/`onLayout`**：无限循环 + 一帧内反复遍历。
6. **动画用 `left/top`**：每帧触发 requestLayout；用 `translationX/Y`、`scaleX/Y` 走属性动画，只走 draw。
7. **`ViewStub` / `merge` / `include`**：减少层级和初始 inflate 成本。
8. **`INVISIBLE` 仍然参与 measure/layout**，只是不绘制；`GONE` 才完全跳过。
9. **`setWillNotDraw(false)`**：自定义 ViewGroup 想让 `onDraw` 生效必须调用（`ViewGroup` 默认优化跳过 `onDraw`）。
